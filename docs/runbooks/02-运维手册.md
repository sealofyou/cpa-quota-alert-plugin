# 02 - 运维手册

## 观测项

- CPA 进程健康。
- systemd timer 是否每 5 分钟触发。
- `POST /v0/management/cpa-quota-alert/check` 返回状态。
- `GET /v0/management/cpa-quota-alert/status` 中的最近可信额度、stale、pending event 和 channel 状态。
- `POST /v0/management/cpa-quota-alert/test-notification` 在 dry-run 与真实通知阶段的结果。
- CPA request log 是否开启、是否短周期轮转、是否限制 root 可读。
- 通知通道送达状态。

## systemd 运维

```sh
systemctl status cpa-quota-alert-plugin.timer
systemctl list-timers cpa-quota-alert-plugin.timer
journalctl -u cpa-quota-alert-plugin.service
```

`cpa-quota-alert-plugin.service` 是 oneshot，不是常驻进程。它以 `root` 运行，仅用于读取 root-owned `0600` curl config 中的 Management Key；不要放宽 `curl.conf` 权限。它只调用本机 loopback Management endpoint，不负责加载插件，也不读取 `plugin.env`。

`/etc/cpa-quota-alert-plugin/curl.conf` 必须 root-owned、mode `0600`，并且是唯一保存 CPA Management Key 的 systemd-side 文件。

## Secret 与配置变更

- 通知 secret 放在 CPA service drop-in 引用的 EnvironmentFile 中。
- `deploy/systemd/cpa-service-plugin-env.conf.example` 要安装到实际 CPA systemd service 的 `.service.d/` 目录；服务名取决于 CPA 安装方式。
- 同一 drop-in 使用 `StateDirectory=cpa-quota-alert-plugin` 与 `StateDirectoryMode=0700` 创建 `/var/lib/cpa-quota-alert-plugin`，匹配示例配置的 `state_path`。
- 本地 `CPA_QUOTA_ALERT_SMTP_PASSWORD` 值就是实际 SMTP 密码；仓库示例值必须保持虚构。
- env 文件使用 root-owned `0600` 权限，且不入 Git。
- 修改通知 secret 后，运行 `systemctl daemon-reload` 并受控重启 CPA；插件注册后才能看到新的 env。
- CPA restart 后验证 state 目录存在、owner 是实际 CPA service 身份、mode 是 `0700`，并确认实际 CPA service 可写。
- 如果 `StateDirectory` 不可用，手工创建 `/var/lib/cpa-quota-alert-plugin`，赋给实际 CPA 用户和组，并保持 mode `0700`。
- 修改 timer 或 oneshot unit 后，运行 `systemctl daemon-reload` 并重启 timer。
- 不在 state、日志、README 命令行或插件 YAML 中记录真实 secret；state 不得 world-readable。

## 常见风险

- `wham/usage` 响应结构变化。
- `Chatgpt-Account-Id` 可能进入 CPA request log。
- 单账号 401 或凭据错误被误判为整池失败。
- 未知套餐被误算为零或默认权重。
- pending event 因通知通道失败而重复发送。
- 插件 panic 影响 CPA 进程稳定性。

## 运行原则

- VPS1 只放插件和 timer 资产，不额外安装插件常驻服务。
- 不为部署该插件而升级或降级 CPA。
- 所有生产切换先 dry-run，再人工确认测试通知。
- VPS2/VPS1 dry-run 前先验证 state 目录写权限。
- Pro、K12 或其他套餐权重都属于 operator 配置，不作为官方事实对外表述。
- 回滚先停 timer，再禁插件，最后才受控重启 CPA。
