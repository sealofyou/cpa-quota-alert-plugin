# 01 - 部署手册

## 当前阶段

当前仓库处于 pre-alpha implementation 阶段。已有 systemd timer、oneshot service、curl config 示例、插件配置示例和通知 env 示例，但 release Gate 尚未完成。

不得声称已经完成 Linux 或 VPS 验证。生产启用前仍需补齐 Linux amd64 `.so`、SHA-256 checksum、Linux systemd verify、VPS2 隔离 dry-run、VPS1 三轮 dry-run、通知测试和回滚演练。

## Secret 边界

- CPA Management Key 只能放在 `/etc/cpa-quota-alert-plugin/curl.conf` 这类 root-owned `0600` curl config 中。
- Management Key 不得进入 systemd `ExecStart`、Environment、插件 YAML、README 命令行、日志或 state。
- `plugin.env.example` 只用于 CPA service drop-in 的 EnvironmentFile，不被 oneshot service 使用。
- drop-in 必须安装到实际 CPA systemd service 的 `.service.d/` 目录；服务名取决于 CPA 安装方式，本仓库不假设固定名称。
- drop-in 使用 `StateDirectory=cpa-quota-alert-plugin` 与 `StateDirectoryMode=0700`，由 systemd 按实际 CPA service 身份创建 `/var/lib/cpa-quota-alert-plugin`。
- 复制出的 env 文件必须 ignored、root-owned、mode `0600`，永不入 Git。
- 本地 `CPA_QUOTA_ALERT_SMTP_PASSWORD` 值就是实际 SMTP 密码；仓库示例值必须保持虚构。
- 修改通知 secret 后，需要 `systemctl daemon-reload` 并受控重启 CPA，让同进程插件注册时读取新环境。

## systemd 安装

```sh
sudo install -d -o root -g root -m 0750 /etc/cpa-quota-alert-plugin
sudo install -o root -g root -m 0600 deploy/systemd/curl.conf.example /etc/cpa-quota-alert-plugin/curl.conf
sudo install -o root -g root -m 0600 deploy/systemd/plugin.env.example /etc/cpa-quota-alert-plugin/plugin.env
sudo install -o root -g root -m 0644 deploy/systemd/cpa-quota-alert-plugin.service /etc/systemd/system/cpa-quota-alert-plugin.service
sudo install -o root -g root -m 0644 deploy/systemd/cpa-quota-alert-plugin.timer /etc/systemd/system/cpa-quota-alert-plugin.timer
```

启动 timer 前，先编辑 `/etc/cpa-quota-alert-plugin/curl.conf`，替换 fake Management Key，并确认 loopback CPA Management 端口。

将 CPA service env drop-in 安装到实际 CPA service 名下：

```sh
sudo install -d -o root -g root -m 0755 /etc/systemd/system/<actual-cpa-service>.service.d
sudo install -o root -g root -m 0644 deploy/systemd/cpa-service-plugin-env.conf.example /etc/systemd/system/<actual-cpa-service>.service.d/cpa-quota-alert-plugin-env.conf
sudo systemctl daemon-reload
sudo systemctl restart <actual-cpa-service>.service
sudo systemctl enable --now cpa-quota-alert-plugin.timer
```

将 `<actual-cpa-service>` 替换为真实 CPA systemd service 名。oneshot service 以 `root` 运行，仅用于读取 root-owned `0600` curl config 中的 Management Key；不要放宽 `curl.conf` 权限。它只调用 `curl --config /etc/cpa-quota-alert-plugin/curl.conf`，由 curl config 负责 POST `{}` 到 `http://localhost:8080/v0/management/cpa-quota-alert/check`。oneshot timer 不读取 `plugin.env`。

CPA restart 后，验证 `/var/lib/cpa-quota-alert-plugin` 存在、owner 是实际 CPA service 身份、mode 是 `0700`，并确认实际 CPA service 对该目录有写权限。若宿主 systemd 版本或部署策略不支持 `StateDirectory`，手工创建同目录，赋给实际 CPA 用户和组，并保持 mode `0700`。插件 state 不得 world-readable。

## CPA 配置

先使用 `examples/plugin-config.yaml`，保持 `dry_run: true`。该配置只包含公开保守的 Plus/Team `1x 7d` 规则，Free ignored，Webhook 默认 disabled。

只有 operator 已经本地确认 Pro20x、K12 等权重时，才参考 `examples/operator-confirmed-pro20.yaml`。该示例不是 OpenAI 官方事实。

## 上线顺序

1. VPS2 dry-run 前先验证 state 目录 owner、mode 和写权限。
2. VPS2 隔离 CPA 实例加载插件，使用 dry-run 和假通知配置。
3. 在 VPS2 检查 `check`、`status`、`test-notification` 三条 Management route 的 dry-run 响应。
4. VPS2 行为符合预期后，把插件和 timer 资产放到 VPS1。
5. VPS1 dry-run 前先验证 state 目录 owner、mode 和写权限。
6. VPS1 不新增额外常驻服务；只让 CPA 加载插件，并用 systemd timer 触发 check。
7. VPS1 连续三轮 dry-run，与旧监控结果对齐。
8. operator 确认后，测试通知。
9. operator 再次确认后，启用真实通知发送。

## 回滚

1. 停用 `cpa-quota-alert-plugin.timer`。
2. 在 CPA 配置中禁用插件。
3. 如热加载无效，恢复旧 CPA 配置并受控重启 CPA。
4. 确认 CPA 核心请求恢复。

回滚不升级 CPA，不降级 CPA，不删除、不禁用、不刷新 CPA auth。
